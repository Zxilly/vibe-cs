# 信息架构重构 PRD —— 以用户动线为主轴，以「作品」为中心对象

- 日期：2026-08-19
- 状态：待评审（ready-for-agent 之前的最后人工闸门）
- 前置文档：`2026-08-15-frontend-redesign-design.md`（下称「重设计 spec」）。本文档只取代其 §7 路由表与导航层的决策；其技术选型、§2 分层约束、§3 token 体系、§4 状态与数据、§5 i18n、§6 测试策略、§8 响应式继续有效，本 PRD 不再复述。
- 约束来源：2026-08-19 产品审视结论 —— 全量重构信息架构；**已有数据分析能力全部保留**，只重新归位，不删除。

---

## Problem Statement

从用户视角：

用户打开这个应用时，脑子里只有三种意图：**「继续做上次没做完的那条视频」「做一条新视频」「看看素材和数据」**。但现在的界面把这三种意图埋在了一张按系统模块划分的导航表里：

- 导航暴露的是内部数据模型而不是任务：方案、变更、会话、镜头、合辑、工程、输出、任务记录——用户必须先学会八个术语才能点下第一下。
- Agent 有三个入口（左侧导航「Agent 创作」、右缘「AI 工作台」竖条、几乎每个页面右上角的「用 Agent 制作视频」），用户不知道哪一个是"真的"入口。
- 首页是一块监控面板：进度条、任务 UUID、失败日志占据首屏，而"继续做/开始做"没有位置。
- 「制作」组里四条路径并列（Agent 创作 / 录制计划 / 快速合辑 / 多轨编辑），没有表达"简单路径 vs 高级路径"的分层，用户不知道选哪条。
- 同一批任务记录出现在四个地方（首页进行中、录制计划右列、交付-任务记录、底部导航），内容互相复制。
- 制作一条视频的主线动作（选素材 → 挑镜头 → 剪辑 → 录制 → 导出）散落在五个页面之间，每一步都是死胡同，没有"下一步"的承接。

一句话：**现在的信息架构是按系统模块划分的，而用户是冲着一条做视频的流水线来的。**

## Solution

从用户视角：

**以用户动线为主轴重排导航，以「作品」为中心对象收敛创作流程。**

用户的动线只有一条主线：**获取素材 → 研究数据 → 创作成片 → 拿走文件**。导航因此只有五个目的地，名字就是动线的阶段：

1. **工作台** —— 枢纽。回答三个问题：什么需要我处理？我上次的进度在哪？现在怎么开始？
2. **素材** —— Demo 资料库与 Steam 比赛历史合并为一个素材中心：素材从哪来、分析到哪一步，都在这。
3. **数据** —— 玩家目录与证据检索。复盘、挑人、找片段的研究型能力。
4. **作品** —— 全部视频项目的列表。每条视频是一个「作品」，点进去是带步骤条的作品工作区：**选材 → 剪辑单 → 录制 → 导出**。
5. **成品** —— 输出文件库：做好的成片、缺失文件的管理。

配套收敛：

- **Agent 只有一个入口**：作品工作区「剪辑单」步骤里的 Agent 面板。右缘竖条删除；各页面的「用 Agent 制作视频」统一为「新建作品」；Ctrl K 命令面板保留 Agent 命令。
- **任务记录不再是导航项**，改为标题栏的活动抽屉（铃铛 + 未读计数）。它是日志，用户出问题时才看，不是日常目的地。
- **术语统一**：方案→剪辑单，变更→修改，会话→对话，镜头→片段，合辑/工程→作品，输出→成品文件，任务记录→后台任务。导航、标题、空态、按钮先改；数据模型与 IPC 契约的命名不动。
- **全部数据分析能力保留**：比赛工作区九个视图、证据检索、玩家目录与选手档案、热力图、雷达、回放、AI 点评——一个不少，只是重新归位（见 Further Notes 的保留清单）。

## User Stories

### 工作台

1. 作为集锦创作者，我希望打开应用第一眼看到"什么需要我处理"（待确认的剪辑单、可重试的失败、环境问题），以便我不用翻五个页面找待办。
2. 作为集锦创作者，我希望待办里的每一项都带它自己的动作按钮（审阅、重试、去设置），以便我原地处理，不用跳走。
3. 作为集锦创作者，我希望看到"继续"区块列出我最近编辑的作品及其所在步骤（选材中/剪辑中/待录制/可导出），以便我一下回到上次离开的地方。
4. 作为集锦创作者，我希望"新建作品"是首页最显眼的动作，以便做新视频不用先学术语。
5. 作为集锦创作者，我希望新建作品时可以直接从素材里挑一场比赛作为起点，以便跳过空白页。
6. 作为集锦创作者，我希望首屏不再出现任务 UUID 和进度条墙，以便我专注于内容而不是系统状态。
7. 作为集锦创作者，我希望后台任务的进展收进标题栏的铃铛里并有未读计数，以便我需要时一眼能看到，不需要时不占屏幕。
8. 作为第一次使用的用户，我希望工作台在素材为空时告诉我第一步是导入 Demo，以便我不会面对六个空面板。

### 素材

9. 作为集锦创作者，我希望「素材」一个目的地里既有本地资料库也有 Steam 比赛下载，以便获取素材不用在两个导航项之间猜。
10. 作为集锦创作者，我希望每条素材上都看得到分析状态（未分析/分析中/已就绪/失败），以便我知道哪些比赛可以直接拿去挑镜头。
11. 作为集锦创作者，我希望从素材行上就能"新建作品（以这场比赛为起点）"，以便从素材到创作有直接的承接。
12. 作为集锦创作者，我希望导入 Demo、监听目录、Steam 下载的入口都在素材中心里，以便素材的三种来源在一处管理。
13. 作为集锦创作者，我希望已删除/缺失文件的素材有明确状态和恢复路径（同现状），以便资料库可信。

### 数据

14. 作为复盘型用户，我希望玩家目录保持顶级可达，以便我常看的选手数据不用钻进二级页面。
15. 作为复盘型用户，我希望选手档案、热力图、趋势图保持现状可用，以便我的研究流程不受影响。
16. 作为复盘型用户，我希望证据检索保持跨比赛检索能力，以便我能按选手/地图/武器/事件类型在全库找片段。
17. 作为集锦创作者，我希望从证据检索结果可以直接"加入作品"或"以它为起点新建作品"，以便研究成果直接进入流水线。
18. 作为复盘型用户，我希望比赛工作区的九个视图（概览/回合/选手/对位/道具与经济/回放与热力图/高光/Review 与注释/队伍）完整保留，以便分析能力不因导航重构而缩水。

### 作品（列表与工作区）

19. 作为集锦创作者，我希望「作品」列表列出我所有的视频项目及其当前步骤和状态，以便我管理全部半成品和成品。
20. 作为集锦创作者，我希望每条作品是一个聚合体：关联的比赛素材、剪辑单、录制任务、成品文件都在它下面，以便我不必在五个页面之间手动拼接上下文。
21. 作为集锦创作者，我希望作品工作区顶部有步骤条（选材 → 剪辑单 → 录制 → 导出），以便我永远知道自己在哪一步、下一步是什么。
22. 作为集锦创作者，我希望步骤条告诉我哪一步还不能走以及为什么（例如"还没有片段，不能开始录制"），以便门控是可理解的而不是死按钮。
23. 作为集锦创作者，我希望在「选材」步看到这条作品关联的比赛和已收集的片段，以便素材上下文集中。
24. 作为集锦创作者，我希望从比赛工作区的任意片段/高光/回合可以"加入作品"，并在选材步看到它们，以便挑选动作直接汇入作品。
25. 作为集锦创作者，我希望「剪辑单」步就是镜头列表本身，片段的增删、排序、时长调整都在这里，以便剪辑单是可读可改的一张单子。
26. 作为集锦创作者，我希望剪辑单可以用三种方式编辑——Agent 对话、快速排序、多轨精剪——且在工作区页内切换，以便我按这条视频的复杂度选工具，而不是在导航里赌。
27. 作为集锦创作者，我希望 Agent 对话面板能理解我的剪辑单上下文（"把 02 再短一点"），以便我不用重复描述素材。
28. 作为集锦创作者，我希望 Agent 给我的每一轮修改可以逐条接受或拒绝（同现有变更模型），以便我保持最终剪控制权。
29. 作为集锦创作者，我希望手动排序的修改不会打断 Agent、也不需要它批准（同现状），以便两条编辑路径互不阻塞。
30. 作为集锦创作者，我希望多轨精剪就是现有的多轨编辑器能力（轨道、入点出点、预览），以便复杂作品不缺工具。
31. 作为集锦创作者，我希望「录制」步列出这条作品的录制队列与每个片段的录制进度，以便录制过程可见可取消。
32. 作为集锦创作者，我希望录制环境未就绪时（如缺编码器、HLAE 未托管）录制步给出明确原因与设置入口（同现有降级规则），以便失败可诊断。
33. 作为集锦创作者，我希望「导出」步让我确认输出设置并看到导出的成品文件，以便作品的终点落在文件上。
34. 作为集锦创作者，我希望快速剪辑工程和多轨工程这两种既有工程类型在作品里以"剪辑模式"呈现，以便旧工程不丢失、可继续编辑。
35. 作为集锦创作者，我希望我现存的每一个旧合辑/多轨工程自动变成一个作品（1:1 包裹），以便重构后我的东西都在。

### Agent（单入口）

36. 作为集锦创作者，我希望 Agent 的入口全应用只有一个——作品工作区的 Agent 面板——以便我不再面对三个入口猜哪个是真的。
37. 作为集锦创作者，我希望各页面原先的「用 Agent 制作视频」变成「新建作品」，以便动作名称与结果一致（Agent 是新建后的一种编辑方式，而不是另一个产品）。
38. 作为集锦创作者，我希望 Ctrl K 命令面板里仍能用命令发起 Agent 相关动作，以便键盘流不受影响。
39. 作为集锦创作者，我希望会话历史、方案修订记录随作品保留可查（同现有持久化），以便我回看这条视频是怎么一点点改出来的。

### 成品与后台任务

40. 作为集锦创作者，我希望「成品」是我的输出文件库：成片列表、大小、位置、缺失状态，以便我找到要发出去的文件。
41. 作为集锦创作者，我希望缺失文件的管理（定位、移除记录、清理无效记录）保持现状可用，以便磁盘整理不被打断。
42. 作为集锦创作者，我希望后台任务（分析、下载、录制、导出）收在活动抽屉里，点一条能看到阶段与日志（同现有任务详情），以便排障时信息不缩水。
43. 作为集锦创作者，我希望失败的任务在抽屉里有明显的重试入口，并且会在工作台"需要我处理"里出现一次，以便失败不被埋掉也不被重复打扰。

### 通用

44. 作为集锦创作者，我希望全应用的术语一致：剪辑单、修改、对话、片段、作品、成品文件、后台任务——以便我只学一套词。
45. 作为集锦创作者，我希望所有页面标题、面包屑、空态、按钮使用同一套术语表，以便没有页面还讲旧话。
46. 作为集锦创作者，我希望旧地址（书签里的 /agent、/recording、/montage、/editor 等）重定向到对应的新位置，以便老链接不死。
47. 作为集锦创作者，我希望折叠态（1100px 以下）与 200% 缩放下新导航和新工作区依然可用（延续重设计 spec §8），以便小窗不被放弃。
48. 作为使用读屏软件的用户，我希望新导航、步骤条、活动抽屉都有正确的可访问名称与状态播报（延续现有 aria 约定），以便重构不牺牲可访问性。
49. 作为集锦创作者，我希望浅色/深色主题在新页面上表现一致（延续 token 反转表），以便主题切换没有死角。
50. 作为集锦创作者，我希望「设置与诊断」「恢复中心」「使用引导」的位置和行为不变，以便重构只动该动的。

## Implementation Decisions

### 模块划分（六块，沿现有前端分层落位）

1. **壳层 IA 重组**（app 层）
   - 导航注册表改为五目的地结构：工作台 / 素材 / 数据 / 作品 / 成品，页脚设置不变；右缘 Agent 竖条整体移除。
   - 路由表重组：新路由 `/projects`、`/projects/:projectId`（`?step=select|shotlist|record|export`）；`/history` 并入 `/library?view=steam`；`/evidence` 并入数据组或降级为比赛工作区视图（见决策 D4）。
   - 旧路由全部 redirect：`/agent` → `/projects`（无作品时）或对应作品剪辑单步；`/recording` → `/projects?step=record` 聚合视图或活动抽屉；`/montage/:id`、`/editor/:id` → `/projects/:id?step=shotlist`（精剪模式）；`/delivery?view=tasks` → 成品页 + 自动打开活动抽屉。
   - 三表绑定（路由表 / 导航注册表 / Ctrl K 命令注册表）的现有约束机制延续，新表同样被 `matchRoutes` 测试锁死。

2. **工作台首页重构**（pages）
   - 三区块：需要我处理 → 继续 → 新建。数据源全部复用现有 query 层（plans/tasks/projects/outputs/config），不新增 IPC。
   - 任务进度墙下线，迁入活动抽屉；环境提示（NVENC 等）保留为"需要我处理"的一等条目。
   - FirstRunStrip 逻辑保留，改写为"新建"区块的空态引导。

3. **作品对象与作品工作区**（domain + pages，本次重构的核心新增）
   - 新增聚合「作品」：一个容器对象，引用现有实体——关联比赛（demoIds）、剪辑单（agent plan 或镜头列表）、剪辑模式（快速/多轨工程引用）、录制任务、输出文件。**优先用现有 IPC 聚合拼装**；若契约缺口无法绕过，单独立项补契约，不在本 PRD 里偷渡后端改动。
   - 工作区 = 步骤条 + 四个步骤视图。步骤门控规则显式建模（无片段不能录制、未确认剪辑单不能导出等），与现有 xstate 任务生命周期同构。
   - 步骤条是导航元件不是向导：允许任意回退，不锁定顺序。
   - 迁移：现存的 montage/editor 工程与 agent plan 在首次读取时各包一层作品（1:1），UI 不写迁移向导。

4. **素材中心**（pages 合并）
   - `/library` 吸收比赛历史/Steam 下载为第二视图；现有 LibraryTable/LibraryCards、筛选、列配置、视图保存全部保留。
   - 行级动作新增"新建作品（以此为起点）"。

5. **成品中心 + 活动抽屉**（pages + app 层）
   - 成品页 = 现有输出视图（含清理、定位、删除对话）不变，摘掉任务记录 Seg。
   - 活动抽屉挂在壳层标题栏：未读计数、分状态列表、条目打开现有任务详情（TaskDetail 能力保留，从抽屉以覆盖层呈现）。
   - 失败任务同时上首页"需要我处理"，去重规则：同一任务在两处的入口指向同一详情。

6. **术语层**（i18n 文案 + 一处映射表）
   - 单一映射表定义新旧术语对应（方案→剪辑单、变更→修改、会话→对话、镜头→片段、合辑/工程→作品、输出→成品文件、任务记录→后台任务），页面文案逐页替换。
   - 数据模型、IPC、存储键名、测试 fixtures 的英文标识符不改——术语层只管 UI 文案。
   - 英文 locale 走现有 extract/compile 流程同步更新。

### 关键决策

- **D1 设计系统不动**：tokens、primitives、layout、Blueprint（安静发丝框）、控制高度与间距节奏全部沿用。本重构是信息架构与页面组合的变化，不是视觉体系的变化。
- **D2 保留清单即验收线**：Further Notes 的能力保留清单逐条对应现有测试；重构完成定义为"清单每条仍可达且测试不删只改"。
- **D3 后端零改动目标**：作品聚合优先纯前端拼装；任何新契约需求单独立项，不阻塞阶段 1。
- **D4 证据检索的归位**：保留顶级（「数据」组，与玩家目录并列），因为它是跨比赛检索，不隶属于单场比赛；比赛工作区内的证据入口保留现状。相比初版审视的"并入工作区"，这是能力保留约束下的修正。
- **D5 Agent 单入口**：右缘竖条删除，不做"保留为快捷方式"的妥协——三个入口减到一个，不是减到两个。
- **D6 步骤条门控显式化**：门控原因必须是一句话（"还没有片段"），不允许无解释禁用——延续现有 `disabledReason` 约定。
- **D7 分阶段落地，每阶段可独立验收**：
  - 阶段 1：术语层 + 首页三区块 + 活动抽屉 + 导航重排 + 右缘竖条移除（页面内部不动，风险最低，先行）
  - 阶段 2：作品对象 + 作品列表 + 工作区骨架（步骤条 + 门控）+ 旧路由 redirect
  - 阶段 3：Agent 面板 / 快速剪辑 / 多轨精剪迁入工作区，录制队列迁入，旧页面退役
  - 阶段 4：素材中心合并（history 入 library）、收尾与旧代码删除

## Testing Decisions

好测试的定义（与现状一致）：只测外部行为——渲染出的可访问名称、路由可达性、状态机转移、门控文案；不测类名、组件树形状等实现细节。

- **三表绑定**：现有 `router.test` 用 `matchRoutes` 锁路由/导航/命令面板三表一致；新 IA 的同型测试必须先红后绿，旧路由 redirect 逐条断言。
- **作品状态机**：步骤门控用状态机建模，单测覆盖全部合法/非法转移（先例：`data` 层的 xstate 任务生命周期测试）。
- **步骤条与门控**：交互测试断言门控文案即禁用原因（先例：`*interaction.test.tsx` 的 jsdom + testing-library 写法）。
- **首页三区块**：骨架测试断言三区块存在与顺序（先例：`pageSkeleton.test.tsx`）；空态/服务降级态各一条。
- **活动抽屉**：交互测试覆盖未读计数、打开详情、失败后两处的去重入口。
- **术语一致性**：locale 覆盖率测试（现有 `localeCoverage.test.tsx`）延续；新增"旧术语不出现在 chrome 层文案"的快照断言。
- **能力保留回归**：保留清单对应的现有测试只允许改断言位置，不允许删除；`pnpm lint && pnpm typecheck && pnpm test` 每阶段保持全绿（延续重设计 spec §9 风险 2 的既定纪律）。

## Out of Scope

- Rust 后端、demo worker、分析管线、录制管线的任何改动（D3：契约缺口单独立项）。
- 新的分析能力、新的导出格式、新的 AI 提供方。
- 视觉体系变化：token、配色、字体、控件尺寸、间距节奏一律不动（D1）。
- 移动端布局与新断点；1100px 折叠与 200% 缩放只要求"不坏"，不新增优化。
- 英文文案的润色（走既有 i18n 编译流程，不做人肉审校）。
- 饰品/Demo 改写等既有功能入口的位置调整（维持现状所在页面）。

## Further Notes

### 与重设计 spec 的关系

本文档取代 2026-08-15 spec 的 §7 路由表及由它派生的导航分组（资料库/制作/交付）。§2 分层约束、§3 token、§4 状态与数据模型（含 §4.5 会话/方案/修订模型——它是作品剪辑单的底座，不动）、§5 i18n、§6 测试策略、§8 响应式继续有效。

### 迁移与兼容

- 旧路由 redirect 永久保留（hash 路由，无服务端 301 成本）。

### 遗留风险

- 作品聚合若撞契约缺口（例如"按作品取全部任务"无现成查询），阶段 2 范围需重估——这是阶段 1 先行的原因之一。
- 术语替换面广（约 2000 条 i18n 目录，spec §9 风险 3 已记录），阶段 1 的 extract/compile 节奏沿用既有 CI 门。
