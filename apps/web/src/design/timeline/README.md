# 多轨时间轴技术原型（规格阶段 0.5）

规格：`docs/superpowers/specs/2026-08-15-frontend-redesign-design.md` §0.5、§9 风险 1、§1.2
设计稿：画板「10 多轨编辑器」

这份原型只回答一个问题：**自研多轨时间轴（替代 `@xzdarcy/react-timeline-editor`）能不能做？**
它不接任何真实数据，不接后端，不进路由。下面是如实的结论。

---

## 结论

**能做，而且核心算法比替换掉的库更贴合本产品的需求。**
但工作量被低估了：§0.5 点名的六项能力只是编辑器的一半，
真正难的部分（修剪、拖拽时自动滚动、虚拟化）都不在那六项里，而阶段 3f 必须有。

建议阶段 3f **保留自研方案**，理由不是「已经写完了」，而是第 3 节那一条：
`@xzdarcy` 的数据模型里没有素材入出点，滑移和正确的剃刀在它的模型里根本表达不出来。
但要按第 2 节的清单重新估工时，不要按「§0.5 已经跑通」估。

---

## 1. 做通了的

六项能力全部跑通，每一项都有测试，且都在 node 环境里穷举验证过边界。

| §0.5 要求 | 模块 | 关键结论 |
| --- | --- | --- |
| 剃刀 | `razor.ts` | 两半的 `sourceIn` / `sourceOut` 连续无跳帧；边界上不切（不产生零长片段）；链接组同时切，且**右半重新成组**——否则切完之后拖左边的视频会带走右边的音频 |
| 吸附 | `snapping.ts` | 阈值以像素给（默认 8px），用时除以 `pixelsPerSecond`，所以缩放 4× 之后同样的 0.25 秒就吸不住了；片段左右两条边同时竞争，近的赢；平局按「播放头 > 标记 > 片段边」定序，结果与目标顺序无关 |
| 拖拽 | `dragMove.ts` `dragPreview.ts` | 越界左侧默认钳到 0（不是拒绝），右侧无界；跨轨只允许同类型轨道；链接的伙伴**保持自己的轨道**只平移时间；重叠两种策略都实现了（`reject` 默认 / `overwrite` 会裁剪、一分为二或整条删除） |
| 缩放 | `timeScale.ts` | 位置全部由一个 CSS 变量 `--tl-pps` 决定，片段、播放头、标尺刻度不可能各算各的；`zoomAtAnchor` 保证光标下的时刻不动；缩放时 DOM 节点不重建（有测试断言同一个元素对象还在） |
| 波纹删除 | `rippleEdit.ts` | 三种范围 `track` / `linked` / `all`，默认 `linked`（设计稿要求的「链接的音视频一起动」）；每条轨道按**自己失去的那段**的长度收拢；标记默认不动（标记指的是比赛里的时刻，不是剪辑里的时刻），可选跟随；播放头永不动 |
| 滑移 | `slip.ts` | `start` / `duration` 是不变量，只动 `sourceIn`；越界钳位而不是拒绝；链接组取**最紧的那一个**的余量，两条轨永远不会滑出不同步 |

额外做通、但 §0.5 没要求的：

- **撤销 / 重做**。一次手势一条记录（拖拽过程中不写文档，抬手才提交），所以不需要回滚。
- **全键盘可编辑**。片段是真正的 `<button>`：← → 微调（Shift ×10）、↑ ↓ 换轨、Delete / Shift+Delete、
  S 在播放头切开；标尺是 `role="slider"`，← → Home End 驱动播放头。
  这不是锦上添花——简报 §15.3 要求全流程可键盘完成，而且它让剃刀在 jsdom 里可测。
- **拒绝要出声**。每个操作返回 `{applied, reason}`，界面把 reason 渲染成 `Notice`
  （「这里已经有片段了，没有移动」/「轨道类型不同」），符合设计稿「不隐藏、不静默失败」。
  拖拽过程中就已经在片段上画红，抬手前用户就知道会被拒。

### 架构（这是原型的重点）

```
纯逻辑（node，无 React 无 DOM）        React
─────────────────────────────────    ────────────────────────
timelineModel.ts  文档与查询          ClipView.tsx
timeScale.ts      秒 ⇄ 像素、标尺      TimeRuler.tsx
geometry.ts       轨道高度与命中        TrackHead.tsx
snapping.ts       吸附                Playhead.tsx（含标记层）
razor.ts          剃刀                TimelinePrototype.tsx
dragMove.ts       移动 / 重叠          useTimelineEditor.ts ← 唯一同时认识两边的文件
rippleEdit.ts     波纹删除
slip.ts           滑移
dragPreview.ts    拖拽预览
```

`dragPreview.previewDrag(文档, dx, dy, 缩放, 吸附)` 是分层的关键：
一次 `pointermove` 只提供两个数字，其余全是纯函数推导。所以整套拖拽逻辑
（换轨、吸附、拒绝、要写进 `--tl-dx` 的那个像素值）在 node 项目里就能穷举测，
jsdom 里的指针测试只需要验证「事件确实接上了」。

测试：**257 个用例 / 15 个文件**，按 §6.2 的三个项目分：

| 项目 | 文件 | 用例 | 内容 |
| --- | --- | --- | --- |
| `unit`（node） | 8 | 170 | 纯逻辑，含若干穷举循环（每个内部时刻切一刀、每个像素位移的落点） |
| `markup`（node） | 5 | 34 | `renderToStaticMarkup` 的结构与 aria |
| `interaction`（jsdom） | 2 | 53 | 32 个命令 / 键盘，21 个真指针拖拽 |

### 渲染层

按 §0.5 要求做到了：

- 平移用 `transform: translateX()`，拖拽过程中每帧**只写一个自定义属性** `--tl-dx`；
- 缩放只改容器上的 `--tl-pps` 一个值，片段的 `--tl-t0` / `--tl-dur` 用秒表示、不重算，
  DOM 结构不变（唯一例外：标尺刻度的档位会随缩放换，那是一次性的，不是每帧的）；
- 片段宽度是 `calc(var(--tl-dur) * var(--tl-pps) * 1px)`。宽度仍随缩放变化，
  这是必然的——用 `scaleX` 代替会把边框和文字一起拉变形。

## 2. 做不动 / 没做的

按「阻塞阶段 3f 的程度」排序。**前四条必须补，缺一个都不能算多轨编辑器。**

1. **没有修剪（trim）。** 拖片段的左右边缘改入出点，是 NLE 里使用频率最高的操作，
   §0.5 的六项里没有它，所以这里也没有。它需要边缘命中区、双向的素材余量约束、
   以及和吸附的交互，工作量与「拖拽」一档，不比它小。
   顺带缺的还有 roll（同时改相邻两片段的接缝）和 slide。
2. **拖到边缘不会自动滚动。** `scrollPx` 状态在、`zoomAtAnchor` 也在，但没有滚动条、
   没有滚轮处理、没有「拖到视口边缘自动卷动」。最后一项是这类控件公认的难点
   （要在 rAF 里持续推进并同时重算预览），完全没碰。
3. **没有帧网格。** 时间全是浮点秒，比较靠 `TIME_EPSILON = 1e-6`。
   真实素材是 60fps，入出点必须落在帧上，否则导出会出现半帧。
   量化点应该只有一处（提交前），但 fps 得由工程带进来——现在模型里没有这个字段。
4. **没有虚拟化。** 每个片段一个 DOM 节点，全部渲染。十几条没问题，
   几千条（一场比赛的全部击杀切片）没测过，可能不行。

其余缺口，不阻塞但要知道：

5. **指针捕获没用**。`pointermove` / `pointerup` 挂在 `window` 上，不是 `setPointerCapture`
   ——jsdom 没实现后者，用了测试就跑不了。代价是：拖到浏览器窗口外面松手，
   收不到 `pointerup`，手势会卡住。真实修法是加 `setPointerCapture` 并做能力检测，阶段 3f 补。
6. **只能单选**，没有框选、没有复制粘贴、没有成组。
7. **标记只能读**。模型里有 `markers`，界面上不能新建、不能拖，只有波纹删除能（可选地）推它们。
8. **轨道锁定只有模型**，没有开关它的界面。`overlap: 'overwrite'` 同理：实现了、测了，界面上到不了。
9. **没有速度**。`duration` 恒等于素材时长，100% 速度这个假设写死在 `slipRange` 和剃刀的算术里。
   变速要动模型（加 `speed`，`sourceOut = sourceIn + duration * speed`）。
10. **没有转场、没有关键帧**。设计稿的属性面板画了缩放 / 不透明度 / 音量，这里一个都没接。
11. **片段里没有真实波形和缩略图**。音频片段的条纹是 CSS 渐变，不是数据
    （真波形已有：Rust 侧 `media` crate 算好，见 §1.2）。
12. **性能没有量过**。60fps 是目标，没测，也没做过节流 / rAF 合批。
13. **暗色没有单独核对**。所有颜色都取 token，理论上自动翻转，但没有在暗色下看过。

### 与规格的偏离，各一条理由

- **「标记」不是一条轨道。** §0.5 写的是「多条轨道（视频 / 音频 / 字幕 / 标记）」，
  但设计稿画的是 `top:0;bottom:0` 贯穿全部轨道的两条竖线加顶部标签——那是序列的属性，
  不是某一行的属性。所以 `markers` 是文档上的独立数组，渲染成贯穿的引导线，
  标尺就是它们的「轨道」。要改回一条真轨道，改的是渲染层，模型不用动。
- **片段颜色按轨道类型给，不按片段给。** 依据是画板自己的说明「时间轴颜色只表达轨道类型」。
  画板本身在这一点上自相矛盾（V2 的名牌片段画成了中性色），取说明。
- **控件高度用 32px，不是画稿的 30px。** §3.3 决策 5 明写工具栏在受影响之列。
- **轨道名（V1 / 主画面）不走 Lingui。** 它们是工程文档里的数据，不是界面文案。
  界面文案（工具名、拒绝原因、无障碍名称）全部走宏。

## 3. `@xzdarcy/react-timeline-editor` 哪里比这份原型强

按装在 `node_modules` 里的 1.0.0 逐条核对过（`dist/interface/timeline.d.ts`、
`@xzdarcy/timeline-engine` 的 `TimelineAction`），不是凭印象写的。

**它明确更强的：**

| 能力 | 它 | 这份原型 |
| --- | --- | --- |
| 修剪 | `onActionResizeStart/Resizing/ResizeEnd`，带 `dir: 'left'\|'right'`，`flexible` 逐片段开关 | 无 |
| 拖拽自动滚动 | `autoScroll` 一个布尔 | 无 |
| 行虚拟化 | 基于 `react-virtualized` | 无，全量渲染 |
| 吸附辅助线 | `dragLine` + `getAssistDragLineActionIds`，会画出对齐参考线 | 算得出吸附目标，但界面上不画线 |
| 播放引擎 | `@xzdarcy/timeline-engine`：`play/pause/setPlayRate/setTime`，`effects` 的 `enter/leave` 回调按时间驱动 | 无。播放头只是个数字 |
| 轨道拖拽重排 | `enableRowDrag` + `onRowDragStart/End` | 无 |
| 交互完备性 | 基于 interact.js：指针捕获、触摸、惯性都是它的事 | 手写 window 监听，见上面第 5 条 |
| 滚动同步 API | `setScrollLeft/setScrollTop` + `onScroll` | 有 `scrollPx` 状态，没有配套 API |
| 现成的钩子 | 双击、右键、点击行 / 点击动作 / 点击时间区，一整套 | 只有选中和拖拽 |

**它做不到的，也是不换回去的理由：**

它的编辑单元是 `TimelineAction { id, start, end, effectId, selected?, flexible?, movable?, disable?, minStart?, maxEnd? }`。
**没有素材入点，没有素材时长，没有链接关系。**
后果是硬的，不是风格问题：

- **滑移表达不出来。** 滑移的定义就是「时间轴位置不变、素材入出点平移」，
  而它的模型里根本没有素材入点这个量。
- **剃刀切不对。** 把 `[start,end)` 从中间切成两段它能做，但右半应该从素材的
  `sourceIn + (t - start)` 开始——这个数在它的模型里不存在。要么在旁边再维护一套影子模型
  （那 `onChange` 回来的数据就要每次做双向映射），要么接受切完之后画面跳帧。
- **音视频链接没有**，波纹删除、成组移动、成组滑移都要在外面自己写，
  而它的 `onActionMoving` 只能 `return false` 阻止，不能把伙伴一起挪。
- **吸附是它自己的规则。** `gridSnap` 吸到刻度网格，`dragLine` 吸到别的动作边缘,
  都吸不到播放头和标记，阈值也不是「像素给、随缩放换算」这套（§0.5 明确要求的那套）。
- 视觉语言冲突（自带圆角与主题）、版本停在 1.0.0、额外带进
  `interact.js` + `react-virtualized` + `framework-utils` 三个运行时依赖——§1.2 已经写过。

**一句话**：它在「拖拽控件」这一层比这份原型成熟得多（修剪、自动滚动、虚拟化、播放引擎），
但它的数据模型是「一条时间线上的若干区间」，不是「素材的窗口被摆在时间线上」。
本产品要的是后者。差的那一层是工作量，差的这一层是模型——工作量能补，模型不能。

## 4. 给阶段 3f 的建议

1. 保留 `timelineModel` / `timeScale` / `snapping` / `razor` / `dragMove` / `rippleEdit` / `slip` /
   `dragPreview` 八个纯模块。它们与渲染无关，即使决定换掉整个渲染层也不用重写。
2. 先补第 2 节的前四条（修剪、自动滚动、帧网格、虚拟化），**再**接真实数据。
   顺序反过来的话，性能问题会和数据问题混在一起，分不清是谁的。
3. 帧网格进模型时把 `fps` 放进 `Timeline` 而不是放进每个片段，并且只在提交处量化
   （预览量化会让吸附感觉发涩）。
4. `useTimelineEditor` 目前只管一条时间轴。接真实工程时它要和 `data/` 的
   mutation 对接，撤销栈可能要换成后端权威的版本号——参照 §4.5.3 的第三条规则，
   不要在前端自建第二套修订号。
5. `overlap: 'overwrite'` 已经写好并测过，界面上补一个开关即可，不用重做。
