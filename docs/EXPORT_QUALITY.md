# 导出质量与软件编码

## 产品语义

导出面板的“质量”控制编码失真程度，不是固定文件大小或固定码率。

- 硬件编码继续使用对应编码器的质量参数。
- OpenH264 软件编码与软件回退使用 `qmin = qmax = 35 - floor(quality / 4)`：质量 20 对应 QP 30，80 对应 QP 15，100 对应 QP 10。
- 软件使用固定 QP；这是量化参数控制，不是 CRF，也不承诺不同编码器的相同数字具有相同观感。
- 更高质量、更多像素、更高帧率或更复杂的运动画面，可能产生明显更大的文件。质量 100 仍然不是无损编码。
- 不为软件回退额外强加一个与画面无关的固定码率上限，也不通过丢帧满足文件大小目标。

实现保留同一份 render plan 与 native encoder Interface。`plan.rs` 生成软件 QP 参数，`native_pipeline.rs` 将其传递给 libavcodec。没有新增另一种导出模式或码率设置界面。

## 2026-09-05 实测依据

审查样本为 1920×1080、60 fps 的 6 秒 CS2 高运动镜头；原录制为约 16.2 Mbps、60.032 fps 的 H.264。项目 source range 为 0.25–6.25 秒，speed 1，入场 Fade 0.25 秒。

旧策略仅计算 `500 + quality × 100` kbps：质量 80 固定 8.5 Mbps，即使改成 4K 或更高帧率也不变；质量 100 也只能到 10.5 Mbps。软件回退因此把“质量”变成了不随画面变化的码率预算。

先排除了错误合成：相邻源帧搜索确认导出 5.9 秒对应源 frame 370；同一最小 trim / RGBA / Fade / Overlay 图以旧参数重新编码，抽帧与真实导出逐像素相同。滤镜输出直接保存无损 PNG 没有出现所观察到的拖影。提高软件编码质量后，同一图的块状模糊与运动边缘残留明显减少。

| 同一原生滤镜图 | 原固定 8.5 Mbps | 软件质量 80 / QP 15 |
| --- | ---: | ---: |
| 输出时长、帧数 | 6 秒、360 帧 | 6 秒、360 帧 |
| 文件字节数 | 6,417,804 | 38,915,983 |
| 文件平均码率 | 8.557 Mbps | 51.888 Mbps |
| 对齐帧 RGB MSE | 37.594 | 3.637 |
| 对齐帧 RGB PSNR | 32.38 dB | 42.52 dB |

文件体积约为原来的 **6.06 倍**。新策略在本机这段 6 秒样本上的原生编码耗时为 **4.96 秒**；此数值包含同一滤镜图，不构成其他硬件或其他素材的性能保证。上述像素指标在相同 960×540 抽帧上计算，只用于这个已对齐样本的前后比较，不替代成片回放和主观验收。

30 Mbps 的单独码率对照得到 MSE 5.372，进一步支持压缩预算是主要因素。修复采用真实 QP 控制，而不是把所有软件导出简单改成 30 Mbps。

## 回归

`crates/media/tests/software_quality_acceptance.rs` 通过生产 Project plan 和 native encoder 编码高细节亮度校准序列，逐帧解码后测量实际误差，并检查帧数。旧策略下质量 20 / 80 的亮度 PSNR 约为 20.29 / 20.30 dB；新策略为 31.45 / 45.50 dB。回归要求质量 80 超过 40 dB，并比质量 20 至少改善 8 dB。此校准素材是压力场景，不冒充真实游戏内容。

现有中文字体、叠加、多源区间和混音的真实导出验收继续执行。原始录制文件与既有导出文件均不被覆写。

## 编码器依据

- [FFmpeg OpenH264 编码器文档](https://ffmpeg.org/ffmpeg-codecs.html#libopenh264) 区分码率、帧跳过与编码配置。
- [FFmpeg 8.1 OpenH264 wrapper](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavcodec/libopenh264enc.c#L130-L144) 将 `qmin/qmax` 映射为编码器最小/最大 QP；当前构建通过这些参数控制软件量化。
